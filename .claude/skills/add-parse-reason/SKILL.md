# Добавление нового вида ошибки парсера

Каждый вид ошибки в этом проекте существует сразу в трёх местах. Если изменить
только одно, код либо не скомпилируется, либо ошибка останется непокрытой
тестом, либо в отчётах по `getReason()` появится значение, которое парсер
никогда не выдаёт. Поэтому все три правки делаются вместе.

## Шаг 0. Нужна ли новая причина

`Reason` виден вызывающему коду: по нему группируют ошибки в отчёте
("17 строк с неверной датой"). Новое значение заводи, только если такие
строки нужно считать отдельно от существующих. Если случай по смыслу
подходит под имеющуюся причину (например, нулевая сумма — это
`INVALID_AMOUNT`), используй её и пропусти шаг 1. Если неясно, спроси
пользователя, а не решай молча.

## Шаг 1. Значение в enum

Файл `src/main/java/ru/lab/TransactionParseException.java`, enum `Reason`.
Имя в стиле `UPPER_SNAKE_CASE`, по образцу соседних (`MISSING_DATE`,
`INVALID_AMOUNT`). Добавь в конец списка, чтобы не менять порядок
существующих значений.

## Шаг 2. Проверка в парсере

Файл `src/main/java/ru/lab/TransactionParser.java`. Бросай ошибку только через
приватный `error(line, Reason, detail)`, а не создавай исключение напрямую:
так формат сообщения остаётся единым.

- `detail` пиши по-русски и конкретно: что не так и что ожидалось
  (в духе существующих сообщений). Префикс "Невалидная транзакция" добавляется
  сам внутри исключения, в `detail` его не дублируй.
- Ставь проверку в нужное место порядка: сначала null и пустая строка, затем
  число полей, затем дата, магазин, сумма. Проверка поля идёт до разбора
  значения, чтобы чужое исключение (`NumberFormatException` и подобные) не
  вылетело раньше нашего.
- Парсер должен бросать только `TransactionParseException` для любого входа,
  это его контракт.

## Шаг 3. Строка в тесте

Файл `src/test/java/ru/lab/TransactionParserTest.java`, метод `invalidLines()`.
Добавь `Arguments.of("<строка>", Reason.<ЗНАЧЕНИЕ>)` рядом с родственными
случаями (проверки даты к датам, суммы к суммам). Обычно полезны два-три
примера: типичный и граничный. Не-ASCII символы записывай escape-последовательностью
(`　`), чтобы они были видны в коде.

## Шаг 4. Проверка

Запусти `mvn test` и покажи результат. Если тесты не проходят, найди причину
и исправь, не ослабляя проверку.

## Шаг 5. CLAUDE.md

Если новое правило меняет, какой ввод считается допустимым, добавь одну
строку в раздел "Нюансы" файла `CLAUDE.md`. Если правило очевидно из кода и
не меняет формат, не добавляй.

## Как работать с файлами

Правь файлы обычными правками (инструмент Edit), по одной за раз: пользователь
хочет видеть каждый дифф. Не используй скрипты с регулярными выражениями.
Коммит не делай, пока пользователь не попросит.

## Итог пользователю

Кратко: какую причину использовал или добавил, три изменённых места,
результат `mvn test`, менялся ли `CLAUDE.md`.
